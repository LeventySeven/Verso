> **The Verso seam.** Verso does not own the inference engine. That fixes the design space: for hosted providers (Anthropic/OpenAI/Gemini) Verso lives on the **post-hoc repair + reask** side of the line (BAML/Instructor/Guardrails territory); for local engines (SGLang/vLLM/llama.cpp/Ollama) Verso can *also* push a grammar constraint down the wire (Outlines/XGrammar/llguidance territory) — but must keep the repair path as the universal fallback because (a) not every provider exposes constrained decoding and (b) constrained decoding distorts the token distribution and cannot fix a model that emitted the *wrong* value, only malformed *syntax*. This note extracts both halves at reimplementable depth: the jsonish repair waterfall + SAP cost function (BAML), the mode→provider map + reask loop (Instructor), the schema→FSM `Index` (Outlines), the per-decode-step bitmask contract + TagDispatch (XGrammar), the lazy Earley mask (llguidance), and the Validator/reask contract (Guardrails).

## BAML (BoundaryML)

### What It Is

BAML is a DSL (`.baml` files) compiled by a Rust toolchain into typed client libraries (Python/TS/Go/Ruby). The piece that matters for Verso is **not** the codegen — it is `jsonish`, the Rust crate that takes arbitrary LLM text and a target type and produces a typed value, repairing malformed JSON along the way. BAML's marketing name for this is **Schema-Aligned Parsing (SAP)**. The thesis: never use the model's "JSON mode" or function-calling — let the model write naturally, then parse + repair against the known schema. On the Berkeley Function Calling Leaderboard (n=1000/model) SAP beats native function calling on every model tested: gpt-3.5-turbo 92% (vs 87.5% FC), gpt-4o-mini **92.4% vs 19.8% FC**, claude-3-haiku 91.7% vs 57.3%, claude-3-5-sonnet 94.4% vs 78.1% (KNOWN, SAP blog). The win is largest on small/cheap models — exactly the ones whose function-calling is weakest.

### The jsonish Parser Waterfall (KNOWN — `engine/baml-lib/jsonish/src/jsonish/parser/entry.rs:15-238`)

`parse_func(str, options, is_done)` is a strict ordered cascade. Each stage is gated by a boolean in `ParseOptions` (`parser/mod.rs:8-27`, all default `true`), and the **first** stage that succeeds returns — but its result is wrapped in `Value::AnyOf([candidate], original_str)` so later schema-guided coercion can still fall back to treating the whole thing as a string. The waterfall:

1. **Standard JSON** (`entry.rs:25`). `serde_json::from_str(str)` via a custom `ValueVisitor` (`value.rs:251-330`) that builds the internal `Value` enum directly (no intermediate `serde_json::Value` allocation). If it parses, return `AnyOf([v], str)`. Note: a top-level *number* or *markdown* is force-marked `CompletionState::Incomplete` even on a clean parse (`entry.rs:33-42`) because a bare trailing number in a stream might still be growing (`12` could become `123`); a quoted string is `Complete` because the closing quote proves it ended.
2. **Markdown extraction** (`entry.rs:57`, gated `allow_markdown_json`). `markdown_parser::parse` scans for fenced blocks with two cached regexes: start `(?m)^[ \t]*```([a-zA-Z0-9 ]+)(?:\n|$)`, end `(?m)^[ \t]*```(?:\n|$)` (`markdown_parser.rs:18-27`) — anchored to line start so a ` ```json ` *inside* a string doesn't trigger. If multiple closing fences exist, it prefers the **first** closing fence that yields a successful sub-parse (recurses into `parse_func`). 0 blocks → fall through; 1 block → `Markdown(tag, value)`; N blocks → emit each block, plus an array of all blocks, plus the trailing prose re-parsed in `JsonMarkdownString` mode, all as one `AnyOf`.
3. **Multi-JSON grep** (`entry.rs:139`, gated `all_finding_all_json_objects`). `multi_json_parser::parse` finds *every* balanced `{...}`/`[...]` substring embedded in prose. Each is tagged `Fixes::GreppedForJSON`. This is how SAP handles "Sure! Here is your object: {…}. Let me know if…" — it greps the object out of the yapping.
4. **Fixing parser** (`entry.rs:176`, gated `allow_fixes`). The character-level state machine (below) that repairs unquoted keys, trailing commas, unterminated strings, etc. Results wrapped `FixedJson(v, fixes)`.
5. **As-string** (`entry.rs:226`, gated `allow_as_string`). Last resort: the entire input becomes `Value::String`, completion = `Complete` if `is_done` else `Incomplete`.
6. Else `Err("Failed to parse JSON")`.

`parse()` (`entry.rs:240`) wraps `parse_func` then calls `.simplify(is_done)` (`value.rs:72-102`) which collapses single-element `AnyOf` and drops redundant string-equals-original candidates so the coercer doesn't waste cycles.

**`ParsingMode` re-entry (KNOWN — `parser/mod.rs:29-56`).** When a stage recurses (markdown sub-parse, multi-json), it calls `next_from_mode(mode)` which *disables* the stages already applied, preventing infinite re-grepping. `JsonMarkdownString` keeps `allow_as_string=true` but turns off markdown+multi-json; `JsonMarkdown` turns off as-string too; `AllJsonObjects` only disables the multi-json finder. A `depth > 100` guard (`entry.rs:19`) catches circular recursion.

### The Fixing-Parser State Machine (KNOWN — `parser/fixing_parser/json_parse_state.rs`)

This is the heuristic-repair core a reimplementer must copy. `JsonParseState` (`:26-40`) carries a `collection_stack: Vec<(JsonCollection, Vec<Fixes>)>` (the open containers, stack-based for nesting), a `completed_values` list, and incremental `StringQuoteTracking` (`:11-19`) — a running count of trailing backslashes and unescaped quotes so deciding whether a `"` closes a string is O(1) instead of O(n²) rescan.

`JsonCollection` variants the machine can open: `Object`, `Array`, `QuotedString`, `SingleQuotedString` (LLMs love `'`), `TripleQuotedString` (`"""…"""`), `BacktickString`/`TripleBacktickString` (markdown code), `UnquotedString` (bare `foo: bar`), `TrailingComment` (`// …`), `BlockComment` (`/* … */`). The presence of single-quote, backtick, comment, and unquoted-string collections is the entire repair surface — standard JSON has none of them.

`process_token(token, next)` (`:526-764`) is a dispatch on the top-of-stack collection:
- **Inside Object**: `}` completes; `,`/`:` ignored; anything else → `find_any_starting_value` (start a key or value).
- **Inside Array**: `]` completes; `,` ignored; else start a value.
- **Inside QuotedString**: `"` → call `should_close_string` (peek-ahead heuristic, below); `\` → decode the escape (`\n \t \r \b \f \\ \"`, and `\uXXXX` consumes 5 chars, `:601-650`); else consume.
- **UnquotedString**: consume the char, then `should_close_unescaped_string` decides termination by context.
- **Comments**: `\n` closes a trailing comment; `*/` closes a block comment — comments are parsed then discarded.

**`should_close_string` (the unescaped-quote repair, `:406-521`)** peeks the next non-space char. It closes the string only when the next structural token is *legal for the current position*: in an object key → close on `:` or `}`; in an object value/array → close on `,` (only if the running unescaped-quote count is even — `closing_char_count % 2 == 0`, so `"he said "hi""` doesn't close prematurely), `}`, or `]`; on whitespace it looks further ahead for a closing bracket/comma/comment before deciding. This is what lets an unescaped interior quote survive: a `"` followed by ordinary text does NOT close.

**`should_close_unescaped_string` (the bare-word terminator, `:211-401`)** picks a `Pos` from the *grandparent* on the stack (`InObjectKey`/`InObjectValue`/`InArray`/`InNothing`) and terminates the unquoted run on the delimiter legal for that position (`:` for a key, `,`/`}` for a value, `,`/`]` for an array). It has elaborate logic for `, ` (comma-space): it decides whether the LLM emitted `", "` as a token *inside* a value vs as a real separator by peeking for a following `"` (new key), `//`/`/*` (comment), or newline. When the stream is exhausted with no delimiter it returns `Close(counter, Incomplete)` — and `counter += 1` (`:249,265,381,397`) is a deliberate off-by-one correction so the streaming caller doesn't re-process the final char (there's a dedicated regression test for this at `:926-949`).

`complete_collection(state)` (`:95-135`) pops the top collection, converts it to a `Value`, and attaches it to its parent: into an Object it alternates key/value by comparing `keys.len() == values.len()`; into an Array it pushes; at top level it lands in `completed_values`. If `state == Complete` it calls `value.complete_deeply()` to mark the whole subtree complete.

**The driver loop (reimplementation spec — `fixing_parser.rs:11-98`):** `parse(str)` creates a `JsonParseState`, iterates `str.char_indices().peekable()`, and for each char calls `state.process_token(c, peekable_rest)`; the returned `increments` count tells the outer loop how many chars `process_token` already consumed from the lookahead (so it advances `chars.next()` that many times — this is why the off-by-one `counter += 1` matters). **At EOF, any still-open collections are force-closed with `CompletionState::Incomplete`** (`:48-50`) — this is what makes a truncated stream parse. Return disambiguation (`:54-97`): 0 completed values → error; 1 → return it; N where all are strings → wrap as an `Array` with `Fixes::InferredArray`; N mixed → keep only the Objects/Arrays. Concrete behaviors from the tests: `"[12"` → `Array([Number(12, Incomplete)], Incomplete)` (`:106-124`); `'{"a": 11, "b": 22'` → `Object{a: Number(11, Complete), b: Number(22, Incomplete)}` — the *last* value is Incomplete because no delimiter closed it, earlier ones are Complete (`:127-148`); `"{mykey"` → empty object (no `:` seen yet, no spurious pair); `"foobar"` → `String("foobar", Incomplete)`. A reimplementer can validate against exactly these.

**Markdown multi-block algorithm (`markdown_parser.rs:39-135`):** scan for opening fences; for each, collect all closing-fence candidates and prefer the **first closing fence whose enclosed content sub-parses successfully** (`:59-83`) — but **stop widening the span at a real block boundary**: if another *opening* fence appears between two closing fences, don't merge across it (`:67-72`); only widen across a stray ` ``` ` when there's no opening fence between (handles ` ``` ` embedded inside a JSON string value). The fence tag (after `` ``` ``) becomes the `Markdown(tag, value)` label; trailing prose after the last block is emitted as a `MarkdownResult::String` for separate parsing. This is more careful than a naive "grab between first and last fence" and is the part most reimplementations get wrong.

### SAP Cost Function = the `Flag` scoring table (KNOWN — `deserializer/score.rs` + `deserializer/deserialize_flags.rs`)

The SAP blog says "the simplest cost function could be Levenshtein distance, but we use a custom cost function that takes into account the schema." **That cost function is the `Flag` enum + `score()` impl.** Every coercion the schema-guided pass makes records a `Flag` (a typed edit operation, `deserialize_flags.rs:6-56`), and the candidate's total cost is the sum of flag penalties (`score.rs`, "**lower is better**"). The exact penalty table (`score.rs:34-77`):

| Flag (edit op applied to make data fit schema) | Penalty | Meaning |
|---|---|---|
| `UnionMatch`, `ObjectFromFixedJson`, `InferedObject` | **0** | free — picking a union variant or accepting fixed JSON is not a "cost" |
| `OptionalDefaultFromNoValue`, `ObjectToMap`, `SingleToArray`, `StringToBool/Null/Char/Float`, `FloatToInt`, `NoFields`, `FirstMatch` | **1** | one cheap coercion (wrap single→array, parse `"true"`→bool, etc.) |
| `SubstringMatch`, `ImpliedKey`, `JsonToString`, `ObjectToString`, `ObjectToPrimitive`, `DefaultButHadUnparseableValue` | **2** | a lossy coercion |
| `StrippedNonAlphaNumeric` | **3** | had to strip junk chars to match an enum value |
| `ArrayItemParseError(x, _)` | **1 + x** | per-item failure compounds |
| `DefaultFromNoValue` | **100** | a required field had to be defaulted from nothing — very bad |
| `DefaultButHadValue` | **110** | there *was* a value but it didn't fit and got defaulted — worst |
| `StrMatchOneFromMany(values)` | Σ counts | enum ambiguity cost |
| `ExtraKey` | **1** | superfluous object key (the "strip yapping") |
| `Incomplete`, `Pending`, `ConstraintResults` | **0** | streaming state / asserts are not parse costs |

Composite values sum children **×10**: `List.score = list_flags + 10·Σ item.score`; `Class.score = class_flags + 10·Σ field.score` (`score.rs:20-27`). So a deeply-nested partly-defaulted object is heavily penalized — exactly the edit-distance intuition the blog describes, but type-aware (a `DefaultButHadValue` deep in a tree dominates).

**`pick_best` (the candidate selector, `coercer/array_helper.rs:29-314`)** is where the cost function is *used*. Given N candidate coercions of the same `jsonish::Value` against a `TypeIR`, it (1) scores each (`Err`→`i32::MAX`), (2) sorts by a multi-key comparator that *before* pure score applies semantic tie-breaks: prefer a non-`SingleToArray` list over a coerced one; prefer a list with properly-parsed items over one full of raw markdown strings; prefer a list with fewer `ArrayItemParseError`s; on a union, devalue a class that is just one `ImpliedKey`'d string; devalue a class whose every field is a default; devalue a primitive string that was cast from a composite (`JsonToString`); (3) finally compares `(is_default_empty, score, index)`. The winner gets a `UnionMatch` or `FirstMatch` flag. This is how SAP "picks the best of many candidates."

### Schema-Guided Coercion — two-phase `try_cast` → `coerce` (KNOWN — `coercer/mod.rs:303-317`, `coerce_union.rs`, `coerce_class.rs`, `match_string.rs`)

After the parser produces a `jsonish::Value` (the loose, repaired representation), the **coercer** maps it onto the target `TypeIR`. The `TypeCoercer` trait (`coercer/mod.rs:303-317`) has two methods, and the order is the whole optimization:
- **`try_cast(ctx, target, value) -> Option<BamlValueWithFlags>`** — the *zero-cost, exact* attempt. It returns `Some` only when the value already fits the type with no lossy edits. For a union (`coerce_union.rs:10-57`) `try_cast` tries each variant and **short-circuits the moment one yields `score()==0`** (a perfect match), recording `UnionMatch(idx)`. `ParsingContext.union_variant_hint` (`coercer/mod.rs:30-31,72-87`) carries the variant index that matched the *previous array element* so an array-of-unions tries the likely variant first — a big speedup for homogeneous lists.
- **`coerce(ctx, target, value) -> Result<BamlValueWithFlags, ParsingError>`** — the *lossy, flagged* fallback used when no perfect cast exists. Every edit it makes records a `Flag` (the cost), and `pick_best` (above) ranks the alternatives. This is the layer that does `SingleToArray`, `StringToBool`, `ImpliedKey`, default-filling, etc.

**Recursion + cycle guards:** `ParsingContext` carries `visited_during_coerce` and `visited_during_try_cast` sets keyed by `(class_name, value)` (`coercer/mod.rs:92-112`); a class re-entered on the same value bails (`coerce_class.rs:52-54`) — this is how recursive types (`type A = A[]`) terminate. `enter_scope` pushes a field name onto `scope` so every `ParsingError` carries a dotted path (`display_scope`, `mod.rs:35-39`).

**Class field matching (`coerce_class.rs`):** an `Object` value is matched field-by-field against the class's `FieldValue = (Name, TypeIR, description, streaming_needed)` (`:21`). If a class is `@@stream.done` and we're streaming and the object is `Incomplete`, `try_cast` rejects it outright (`:37-46`) — the streaming-done guard at the class level. Missing fields trigger `error_missing_required_field` (`mod.rs:205-232`) listing exactly which required fields are missing vs which failed to parse, each with its scope path — **this is the structured error a reask would feed back.**

**Enum / literal matching cascade (`match_string.rs:39-130`):** matching an LLM string against enum variants (or their aliases) is a 4-attempt waterfall, escalating leniency and recording the cost: (1) case-sensitive match ignoring punctuation; (2) strip punctuation from both sides, retry; (3) retry again on stripped; (4) **last hope: lowercase, punctuation-stripped match** — with the comment "this could yield wrong results since the name of a candidate could appear as a 'normal' word." Substring matching is gated behind `allow_substring_match` and penalized (`SubstringMatch`=2). Each successful match at a looser tier records the corresponding `Flag`, so a clean exact enum match costs 0 and a lowercased-substring match costs more — feeding back into `pick_best`.

### Streaming Partial Types — `@stream.done` / `@stream.not_null` / `@stream.with_state` (KNOWN — `baml-types/src/ir_type/converters/streaming.rs` + `jsonish/src/deserializer/semantic_streaming.rs`)

BAML's streaming is **type-driven**, not a separate parser. `CompletionState` ∈ `{Pending, Incomplete, Complete}` rides on every `Value`. Three annotations control whether a partial node is *emitted*:

- **`@stream.done`** → `StreamingBehavior.done = true`. A node so marked must be `Complete` or it is *dropped* from the streamed value (`semantic_streaming.rs:85-87` raises `IncompleteDoneValue`, and the parent's `process_node` catches it and replaces the field with `Null`). `required_done` (`:299-360`) also makes types *inherently* done: `Int/Float/Bool/Media/Null` primitives, enums, and literals are always done (a half-streamed `12` is never shown); `String/List/Map/Class` are streamable; a `Union` is done iff all matching variants are done. So by default you never see a partial number or partial enum, only partial strings/lists/objects.
- **`@stream.not_null`** → `StreamingBehavior.needed`. Listed in `class_streaming_needed_fields`. While `allow_partials==true`, if a needed field is null/missing the *whole object* is withheld (`MissingNeededFields`). When streaming finishes (`allow_partials==false`) the check is skipped (`needed_fields` returns empty set, `:284-295`). Lists/maps/union-variants are auto-marked `needed=true` during partialization (`streaming.rs:59,63,75,85,124`).
- **`@stream.with_state`** → `StreamingBehavior.state = true`. Attaches the `CompletionState` to the emitted node's metadata (`Completion{state, display, required_done}`, `:79-83`) so the consumer can render "still typing…" per field.

`from_type_ir` (`streaming.rs:7-213`) is the compiler: it walks `TypeIR` → `TypeStreaming`, making every non-needed, non-optional field into `Union[T, null]` (so a partial object can legally have missing fields), and propagating `done` into list items / map values / union variants. This is the `Partial<T>` type system — generated from the schema, not hand-written. `validate_streaming_state` (`semantic_streaming.rs:34-52`) runs on each parse of the growing buffer: distribute types over the parsed value, compute each node's completion, then `process_node` prunes done-but-incomplete nodes and fills gaps with typed `Null`s — yielding a schema-valid partial object on every token.

**For Verso:**
- **Adopt the jsonish waterfall verbatim as the universal output parser.** The ordered cascade (strict JSON → markdown-fence extract → grep-embedded-JSON → char-level fix → as-string) is the correct fallback chain for *any* provider response, and it is provider-agnostic. Verso owns no inference engine, so this is the path that always works. Port the five stages; the `ParsingMode` re-entry guard and `depth>100` are non-optional correctness details.
- **Steal the `Flag`-table cost function rather than Levenshtein.** A schema-aware edit-cost (`DefaultButHadValue=110` >> `SingleToArray=1`) is what makes SAP pick the *semantically* closest parse, not the lexically closest. Verso's parser should record a typed `Flag` per coercion and pick the min-cost candidate via a `pick_best`-style comparator with the same semantic tie-breaks (devalue all-default classes, devalue string-cast-from-object on unions). The ×10 child multiplier and the 100/110 cliff for required-field defaulting are the load-bearing constants.
- **Two-phase coercion: try exact, then fall back to lossy-and-scored.** Verso's coercer should first attempt a zero-cost `try_cast` (short-circuit on a perfect union variant, carry a variant hint across array elements) and only run the flagged/scored `coerce` path when no exact fit exists. Keep `(type, value)` visited-sets for cycle safety on recursive schemas, and a `scope` stack so every parse error carries a dotted field path. For enum/literal fields, copy the 4-tier match cascade (exact → strip-punctuation → lowercase → substring), penalizing each looser tier — never just `==`.
- **Make streaming type-driven, not a second parser.** Verso should compile its output schema to a `Partial[T]` where scalars are `done` (never emit a half-number), strings/lists/objects are streamable, and a per-field "needed" flag withholds the object until required fields arrive. Re-run the full parse on each chunk (jsonish is cheap and idempotent) rather than maintaining a separate incremental parser — the `CompletionState` on each node gives free "still typing" signals (BAML's `@stream.with_state`).
- **SAP vs constrained decoding is settled for Verso's seam:** SAP is the default (works on every provider, lets the model reason, +accuracy on small models). Constrained decoding is an *optional fast-path* on local engines only. Keep both; never make constrained decoding mandatory.

## Instructor

### What It Is

Instructor is the dominant Python structured-output library. It monkey-patches a provider SDK's `create()` so it grows three extra params — `response_model: type[BaseModel]`, `max_retries`, `context` — and returns a validated Pydantic instance instead of a raw completion. It owns no inference. Its two contributions Verso needs: (1) the **`Mode` enum** = the authoritative map of which structured-output wire-API each provider actually supports, and (2) a **reask retry loop** that feeds the Pydantic `ValidationError` back to the model as a follow-up message. The codebase has been refactored into a `v2/` registry architecture; modes, retry, patch all live under `instructor/v2/core/`.

### The Mode Enum — the per-provider structured-output API map (KNOWN — `instructor/v2/core/mode.py:10-127`)

Every `Mode` value is a string naming *how the request is shaped on the wire*. They cluster into two families plus a deprecation-collapse map. **Tool-call family** (`Mode.tool_modes()`, `:80-105`): `TOOLS` (`tool_call`), `TOOLS_STRICT`, `PARALLEL_TOOLS`, `FUNCTIONS` (deprecated legacy `function_call`), `ANTHROPIC_TOOLS`, `ANTHROPIC_PARALLEL_TOOLS`, `MISTRAL_TOOLS`, `VERTEXAI_TOOLS`, `GEMINI_TOOLS`/`GENAI_TOOLS`, `COHERE_TOOLS`, `CEREBRAS_TOOLS`, `FIREWORKS_TOOLS`, `WRITER_TOOLS`, `BEDROCK_TOOLS`, `XAI_TOOLS`, `RESPONSES_TOOLS` (OpenAI Responses API). **JSON family** (`Mode.json_modes()`, `:108-127`): `JSON` (`json_mode`, raw `{"type":"json_object"}`), `JSON_SCHEMA` (`json_schema_mode`, OpenAI native Structured Outputs via `response_format`), `MD_JSON` (`markdown_json_mode` — ask for JSON in a ```` ```json ```` fence, used by providers with no native JSON mode), `JSON_O1` (o1 reasoning models, no system msg), `ANTHROPIC_JSON`, `GEMINI_JSON`, plus per-provider JSON variants.

`from_provider("anthropic/claude-...")` (`v2/auto_client.py:25-108`) splits the `"provider/model"` string and dispatches to `from_openai`/`from_anthropic`/etc., each with a **per-provider default mode**: most default to `Mode.TOOLS` (`:257,330,393,511,577`), a few to `Mode.MD_JSON` (`:701`) for providers with weak tool-calling. So the recommended-mode-per-provider knowledge is baked into the client constructors, not exposed to the caller. The deprecation map (`DEPRECATED_TO_CORE`, `mode.py:203-250`) is the most useful artifact for Verso: it collapses the 40+ provider-specific modes onto **5 canonical modes** — `TOOLS`, `PARALLEL_TOOLS`, `JSON`, `JSON_SCHEMA`, `MD_JSON`. The comment is explicit: "The provider is determined by the client (from_openai, from_anthropic…), not by the mode." So the correct model is **(provider, canonical-mode) → handler**, with the provider doing the wire-specific shaping. The per-provider JSON modes mostly fall back to `MD_JSON` (Cerebras/Fireworks/Writer/Bedrock/Perplexity/Vertex/Gemini JSON → `MD_JSON`), meaning: *most providers without OpenAI-native structured outputs are served by "ask for JSON in a markdown fence and parse it out."* That is the same fence-extraction problem BAML's jsonish stage 2 solves.

### Mode Dispatch — what each mode sends on the wire (KNOWN — `instructor/v2/core/patch.py` + `providers/openai/handlers.py`)

`patch()` wraps `create()`. Inside the wrapper (`patch.py:170-241`), the flow is: `handlers = mode_registry.get_handlers(provider, mode)` → `handlers.request_handler(response_model, kwargs)` shapes the request → templating → cache lookup → `retry_sync_v2(...)`. Each `(provider, mode)` pair resolves to a `ModeHandlers` bundle of three callables: `request_handler` (model → wire request), `response_parser` (raw response → Pydantic), `reask_handler` (ValidationError → modified kwargs). This registry indirection *is* the "one internal request + N adapters" pattern.

Concrete `request_handler` transforms (OpenAI, `handlers.py`):
- **TOOLS** (`:582-593`): `schema = generate_openai_schema(response_model)`; `tools=[{"type":"function","function":schema}]`; **`tool_choice={"type":"function","function":{"name":schema["name"]}}`** — i.e. *force* that one tool. `strict=True` adds `schema["strict"]=True` (OpenAI strict function calling).
- **JSON_SCHEMA** (`:684`): `response_format={"type":"json_schema", "json_schema": {...,"strict":True}}` with `additionalProperties:False` injected.
- **JSON** (`:756`): `response_format={"type":"json_object"}` and the schema is dumped into the system prompt as text (no native enforcement).
- **MD_JSON**: schema dumped into the prompt, asks for a ```` ```json ```` block; response parsed by extracting the fence.

### The Reask Loop (KNOWN — `instructor/v2/core/retry.py:87-244` + `providers/openai/handlers.py:119-268`)

The retry loop is built on `tenacity`. `retry_sync_v2` (`retry.py:87`): if `max_retries` is an int, build `Retrying(stop=stop_after_attempt(max(max_retries,1)) [| stop_after_delay(timeout)], retry=retry_if_exception_type(ValidationError), reraise=True)`. So it **only retries on `pydantic.ValidationError`** — an API/network error is *not* retried by this layer (it re-raises immediately, `:156-161`). Per attempt:
1. `func(*args, **kwargs)` (the real provider call). Emit `completion_arguments`/`completion_response` hooks. `update_total_usage` accumulates token usage across attempts.
2. `parsed = handlers.response_parser(response, response_model, validation_context=context, strict, stream, is_async)` — extract the tool-args/JSON, then `response_model.model_validate(...)`.
3. On success → `_finalize_parsed_response` (unwrap iterables/adapters, attach `_raw_response`) and return.
4. On `ValidationError e`: append `FailedAttempt(attempt_number, exception=e, completion=response)`; emit `parse_error` hook; **`kwargs = handlers.reask_handler(kwargs, response, e)`** — this mutates the message list — then `raise` to let tenacity loop with the new kwargs.

**The reask message is literally `str(exception)`** (the rendered Pydantic `ValidationError`, which is `e.errors()` formatted with field locs + messages). The framing is mode-specific (`handlers.py`):
- **tools mode** (`reask_tools`, `:119-153`): append the assistant message with its `tool_calls`, then for each tool_call append a `role:"tool"` message with `tool_call_id`, `name`, and content `f"Validation Error found:\n{exception}\nRecall the function correctly, fix the errors"`. This keeps a valid tool-call/tool-result transcript so the next turn is well-formed.
- **JSON modes** (`reask_md_json`, `:194-234`): append assistant message + a `role:"user"` message `"Correct your JSON ONLY RESPONSE, based on the following errors:\n{exception}"`.
- **streaming responses**: can't replay tool_calls, so just append a single user message with the error.

When attempts exhaust, it raises **`InstructorRetryException`** (`:224-232`) carrying `last_completion`, `n_attempts`, `total_usage` (summed across all attempts), `messages`, `create_kwargs`, and the full `failed_attempts: list[FailedAttempt]`. That is the per-attempt observability surface Verso's retry budget should expose.

### Response Parsing — extract then validate (KNOWN — `instructor/v2/core/function_calls.py:91-110`)

The `response_parser` first *extracts* the JSON string from the provider response (for tools mode: `response.choices[0].message.tool_calls[0].function.arguments`; for JSON mode: `message.content`, after fence-stripping in MD_JSON), then validates. The validate step has a strict/loose fork (`function_calls.py:91-110`): if `strict` → `cls.model_validate_json(json_str, context=validation_context, strict=True)` (Pydantic's Rust-side strict JSON validation, no type coercion); else → `json.loads(json_str, strict=False)` (tolerate control chars) then `cls.model_validate(parsed, strict=False)` (allow Pydantic's lenient coercions like `"5"`→`5`). The `validation_context` is threaded all the way through so custom `@field_validator`s can see caller-supplied context. **This is the seam Verso plugs jsonish into:** instead of `json.loads`, run the jsonish repair waterfall, then `model_validate`. The `validation_context` passthrough is worth replicating — it lets validators access request-scoped data (allowed values, user limits) without globals.

### Hooks — the observability seam (KNOWN — `instructor/v2/core/hooks.py:13-201`)

`HookName` (`:13-18`): `COMPLETION_KWARGS` (request args just before the call), `COMPLETION_RESPONSE` (raw response), `COMPLETION_ERROR`, `COMPLETION_LAST_ATTEMPT`, `PARSE_ERROR` (the ValidationError on each failed attempt). `Hooks` (`:67`) is a `defaultdict[HookName, list[handler]]`; `on(name, handler)` registers, `emit(name, *args)` fans out. The retry loop emits `completion_arguments`/`completion_response` around the call and `parse_error` on each validation failure (see retry loop above). This is a clean pub/sub seam decoupled from the retry logic.

**For Verso:** expose the same 5 lifecycle events (request-built, response-received, completion-error, last-attempt, parse-error) as a pub/sub hook registry. An agent framework lives or dies on observability into the *reask* cycle specifically — `PARSE_ERROR` per attempt + per-attempt usage is the minimum to debug why a structured turn took 3 round-trips.

### Streaming `Partial[T]` (KNOWN — `instructor/v2/dsl/partial.py`)

`Partial[Model]` (`:522-633`) is created via `__class_getitem__`: it walks the model's fields and, for each, wraps the annotation `Optional[Partial[annotation, MakeFieldsOptional]]` so *every field becomes optional and recursively partial* (`:256,295`); `create_model(...)` builds the new class and stashes `partial_model._original_model = wrapped_class` (`:631`). Streaming (`model_from_chunks`, `:376-408`): accumulate a `potential_object` string across chunks (after `remove_control_chars`), and on each chunk call `process_potential_object`:
- `parsed = jiter.from_json(json_str.encode(), partial_mode="trailing-strings")` — the Rust `jiter` partial parser (same one PydanticAI uses); `"trailing-strings"` means an unterminated string is kept as its partial content rather than dropped (`:381-383`).
- A `JsonCompleteness` tracker (`is_json_complete`) determines whether the **root** object is structurally closed.
- **If root complete AND has data → `original_model.model_validate(parsed)`** (full validation). **Else → `_build_partial_object` via `model_construct`** (skip validation, store raw partial values; `:108-116`). Nested *complete* sub-objects are validated even mid-stream; incomplete ones are constructed.
- Each step `yield`s the object, so the consumer sees a progressively-filled instance. A final validation runs once the stream is structurally complete (`:402-408`).

This is the key design: **don't validate partial JSON** (it would fail required-field checks), use `model_construct` until the buffer closes. Same conclusion BAML reaches with its `done`/`needed` annotations, by a different mechanism (jiter+completeness-tracker vs. CompletionState on a parse tree).

**`JsonCompleteness` — the sibling heuristic (KNOWN — `instructor/v2/dsl/json_tracker.py:57-96`).** This is how Instructor decides per-field completeness mid-stream without a custom parser. `analyze(json_str)`: first try a *strict* `jiter.from_json` — if it parses, the whole tree is complete (`_mark_all` marks every path). If strict fails (incomplete), re-parse with `trailing-strings` and apply the **sibling heuristic** (`_check_siblings`): *if a value has a next sibling, it must be complete* — because jiter had to finish parsing that value to even discover the next sibling exists; only the **last** value at each level is of unknown completeness. So in `{"a": 11, "b": 22` the field `a` is provably complete (it has sibling `b`), `b` is unknown — exactly mirroring BAML's `Complete`/`Incomplete` result for the same input, derived independently. A reimplementer gets per-field streaming completeness for free from any partial JSON parser that preserves order, with zero extra parsing.

**For Verso:**
- **Adopt the `(provider, canonical-mode) → handler` registry, with 5 canonical modes** (`TOOLS`, `PARALLEL_TOOLS`, `JSON`, `JSON_SCHEMA`, `MD_JSON`). Mode is *not* provider-specific; the provider adapter does the wire shaping. This is the structured-output analogue of the "one engine, N protocol adapters" pattern already in `infra-serving.md`. The handler bundle is exactly three callables: `request_handler`, `response_parser`, `reask_handler`.
- **Default to TOOLS mode with forced `tool_choice`** where the provider supports it (single forced function call is the most reliable extraction), fall back to `JSON_SCHEMA` (OpenAI strict), then `MD_JSON` (fence + jsonish extraction) for providers with neither. The mode table tells Verso exactly what each provider can do — don't probe at runtime.
- **Reask = feed `str(ValidationError)` back, framed per mode.** Verso's self-healing loop should: keep a well-formed transcript (replay the assistant tool_call, answer with a `tool` message carrying the error) and only retry on validation failures, not transport errors (those need a different policy). Cap with a tenacity-style `stop_after_attempt | stop_after_delay` and raise a rich exception carrying per-attempt `completion`, `usage`, and the error chain — Verso needs this for its token-budget accounting (usage must sum across reask attempts, as `_initialize_usage`/`update_total_usage` do here).
- **Stream with construct-not-validate.** Verso's `Partial[T]` should make all fields optional, parse the growing buffer with a partial JSON parser (jiter `trailing-strings`), and only `model_validate` once the root is structurally closed — `model_construct` everything before that. This avoids the "required field missing" false-failures that naive per-chunk validation produces.

## Outlines + outlines-core

### What It Is

Outlines is the reference open-source constrained-decoding library. `outlines-core` is a Rust crate (PyO3 bindings) that compiles `JSON schema → regex → DFA → Index`, where the `Index` is a precomputed transition table `state → {token_id → next_state}` over the model's vocabulary. The Python `outlines` package wraps this as a logits processor for local models (Transformers/llama.cpp/MLX). This is the *eager* school of constrained decoding (full token-level FSM built upfront), opposite to llguidance's lazy approach. Verso won't run the decoder, but it must speak this contract when passing `json_schema`/`regex` down to SGLang/vLLM (both default to xgrammar but support outlines as a backend — see `infra-serving.md`).

### The `Index` Data Model (KNOWN — `outlines-core/src/index.rs:14-260`)

`Index` (`:16-60`) holds: `initial_state: StateId`, `final_states: HashSet<StateId>`, `transitions: HashMap<StateId, HashMap<TokenId, StateId>>`, `eos_token_id`, `vocab_size`. The transitions map is the whole product — for each FSM state, the set of token IDs legal there and the state each transitions to. Public API the inference loop calls:
- `initial_state()` — where decoding starts.
- **`allowed_tokens(&state) -> Option<Vec<TokenId>>`** (`:239-243`) — the legal next tokens at a state = `transitions[state].keys()`. This is what becomes the logit mask.
- **`next_state(&state, &token_id) -> Option<StateId>`** (`:250-255`) — advance after a token is sampled. Returns `None` for EOS.
- `is_final_state(&state)` — whether EOS is allowed (generation may stop).

### Eager FSM Build — `Index::new(regex, vocabulary)` (KNOWN — `index.rs:103-216`)

This is the algorithm Verso must understand to reason about compile cost. (1) `DFA::new(regex)` compiles the regex to a dense DFA (`regex_automata` crate); get the `universal_start_state(Anchored::Yes)`. (2) **BFS over reachable DFA states** (`next_states` stack seeded with start). For each state: if `dfa.next_eoi_state(state)` is a match → it's a `final_state`. Then for **every token in the entire vocabulary** (`:127`), feed the token's *bytes* through the DFA one at a time (`:132-138`); if any byte hits a dead/quit state, skip that token (`continue 'token_loop`). (3) **Usefulness pruning** (`:142-161`): a destination state is kept only if it is a full-match state OR can transition further on at least one byte-class representative (cached in `is_useful_state_cache`; the expensive intermediate check is short-circuited behind the cheap match check). Useful transitions are recorded `transitions[current][token_id] = next_state` and unseen destinations pushed for BFS. (4) If a non-match state ends up with zero valid transitions → `Error::IncompatibleVocabulary` listing the bytes the vocab can't produce (`:180-198`). (5) Finally each final state gets a self-loop on `eos_token_id` (`:202-207`).

**Cost implication:** the build is O(reachable_states × vocab_size × avg_token_bytes) — it touches every token at every state. For a 100k+ vocab and a complex schema this is the "considerable time and computational resources" the doc warns about (`:98-100`). This is the eager-vs-lazy tradeoff: pay it all upfront, then per-token decoding is a single `HashMap` lookup (~nanoseconds). Caching the `Index` per schema is therefore mandatory.

### Schema → Regex Walk (KNOWN — `outlines-core/src/json_schema/`)

`Regex::to_regex(json)` (`parsing.rs:50-64`) dispatches on which JSON-schema keyword is present, in priority order: empty object → `properties` → `allOf` → `anyOf` → `oneOf` → `prefixItems` → `enum` → `const` → `$ref` → `type`. The primitive regexes are fixed constants (`types.rs:5-10`, KNOWN verbatim):
```
STRING_INNER = ([^"\\\x00-\x1F\x7F-\x9F]|\\["\\/bfnrt])
STRING       = "([^"\\\x00-\x1F\x7F-\x9F]|\\["\\/bfnrt])*"
INTEGER      = (-)?(0|[1-9][0-9]*)
NUMBER       = ((-)?(0|[1-9][0-9]*))(\.[0-9]+)?([eE][+-][0-9]+)?
BOOLEAN      = (true|false)        NULL = null
WHITESPACE   = [ ]?                 # exactly: optional single space
```
The `WHITESPACE = [ ]?` choice is load-bearing and documented (`types.rs:13-17`): letting the model pick arbitrary whitespace "led to pathological behaviors, especially for small models" (infinite-whitespace loops), so the structural whitespace is pinned to *at most one space*. String `format` keywords compile to dedicated regexes: `date-time`, `date`, `time`, `uuid` (RFC-9562), `uri`, `email` (RFC-5322) — all KNOWN verbatim at `types.rs:42-50`.

`parse_properties` (`parsing.rs:89-168`) is the object walk: opens `\{`, and for each property emits `{WS}"name"{WS}:{WS}` + the recursively-generated value regex. **Required vs optional is structural**, not a post-check: it finds the last-required-property index; properties before it get a trailing `,`, after it get a leading `,`, and *optional* properties are wrapped `(...)?`. When nothing is required it emits the full power-set of ordered prefixes (`possible_patterns`, `:153-163`) so any subset of optional keys in declaration order is legal. `allOf`→ concatenation, `anyOf`/`oneOf`→ alternation, `enum`/`const`→ literal alternation, `$ref`→ resolve with a recursion-depth guard (`Error::is_recursion_limit` → skip that property, `:122,147`).

### Vocabulary — why the FSM runs on bytes, and array/numeric constraints (KNOWN — `outlines-core/src/vocabulary/mod.rs:66-108`, `json_schema/parsing.rs:562-596`)

`Vocabulary` (`mod.rs:66-68`) is `{ eos_token_id, tokens: HashMap<Token, Vec<TokenId>> }` — a **token's *bytes* map to a list of token IDs** (multiple IDs can decode to the same byte string). `from_pretrained` (`:82-108`) loads an HF tokenizer, **filters prepend normalizers** (`filter_prepend_normalizers` — strips the leading-space normalizer that would otherwise corrupt byte-level matching), and locates the EOS id. This is why `Index::new` feeds *each byte* of a token through the DFA (`index.rs:133`): tokenization is byte-level, so the FSM is defined over bytes and a token is accepted only if *all* its bytes traverse legal DFA transitions. The `IncompatibleVocabulary` error exists precisely because a regex might require a byte the vocabulary can never produce.

Array constraints compile to regex repetition (`parsing.rs:562-596`): `minItems`/`maxItems` → `get_num_items_pattern` → a `{min,max}` quantifier; the array regex is `\[{WS}((item)(,{WS}(item)){n,m}){?}{WS}\]` where the trailing `?` admits the empty array iff `minItems==0`. Unconstrained `items` falls back to a union of all primitive types with a bounded `depth` (default 2) to stop infinite nesting. String constraints (`parse_string_type`, `:380-412`): `minLength`/`maxLength` → `"STRING_INNER{min,max}"` (validated `min<=max`, else `MaxBoundError`); `pattern` → the pattern inlined verbatim (anchors `^`/`$` stripped since the field is already delimited); `format` → the dedicated `date-time`/`uuid`/etc. regex. `enum`/`const` compile to literal alternations (`parse_enum`/`parse_const`, `:234-257`); `$ref` resolves against `$defs` with the recursion-depth guard. So *every* JSON-schema constraint — required fields, optional ordering, array cardinality, string length/pattern, enum membership, numeric format — becomes structural regex, enforced at the token level, with zero post-hoc validation needed. **This is the exact compiler Verso must emit a clean schema for; understanding it tells Verso which schema features are cheap (enum, const, bounded arrays) vs expensive (open `string`, deep recursion, wide `anyOf`).**

### Consumption Contract — Index → bitmask (KNOWN — `outlines/backends/outlines_core.py:19-90`)

The per-decode-step contract a serving engine implements: build one `Guide(index)` per sequence in the batch (`:79`), `allocate_token_bitmask(vocab_size)` once (`:80-82`), and each step: `guide` exposes the current allowed set, `fill_next_token_bitmask(guide, bitmask)` writes the int32 bitset, then `apply_token_bitmask(logits, bitmask)` sets disallowed logits to `-inf` before sampling. After sampling, `guide.advance(token)` (≡ `index.next_state`). Bitmask kernels exist for torch/numpy/mlx. **This is the same `apply_token_bitmask` contract XGrammar exposes** — the bitmask interface is the de-facto standard between a grammar engine and a sampler.

### Coalescence (KNOWN — blog.dottxt.ai/coalescence.html)

Tokenizer training guarantees redundancy: if `{"` is a token, then `{` and `"` are too — so many token *sequences* reach the same FSM state producing the identical string. The optimization: **"When, in a given transition, several tokens share the same prefix, only keep the transition that corresponds to the longest one."** In their example this cut model calls from 9 to 2 — "at least a 5x speedup over structured generation in Outlines." **The caveat is critical and directly relevant to Verso:** different token paths to the same string yield *different conditional distributions at subsequent positions*, so greedily forcing the longest token "risks degrading output quality if the wrong token path is selected" — i.e. coalescence trades correctness of the probability model for speed. This is the schema-design lesson: a schema that admits many redundant tokenizations wastes inference budget *and* (if coalesced) distorts sampling.

**For Verso:**
- **Know the `Index` is the contract, but never build it.** When Verso targets a local engine (SGLang/vLLM/Ollama) it should pass a `json_schema` or `regex` string down the wire and let the engine's grammar backend build the `Index`/grammar. The mental model to carry: a grammar constraint reduces, per step, to `allowed_tokens(state)` → bitmask → `-inf` masking → `next_state(state, sampled)`. Verso's job is to *produce a clean regex/schema*, not to decode.
- **Schema compilation is expensive and cacheable — cache per schema, reuse across turns.** The eager `Index` build is O(states × vocab). Verso should treat a compiled schema as a reusable object keyed by (schema, model-vocab), not recompile per agent call. (XGrammar's Cross-Grammar Cache, below, formalizes this.)
- **Emit schemas that minimize redundant tokenization and pinned whitespace.** Copy `WHITESPACE=[ ]?` (pin structural whitespace to ≤1 space) to avoid the small-model whitespace pathologies. Prefer `enum`/literal constraints and avoid wide-open `string` fields where a `format` regex would do — every unconstrained span is where the model can drift and where coalescence-class redundancy bloats the FSM.
- **Constrained decoding cannot fix wrong values, only illegal syntax — and it perturbs the distribution.** The coalescence caveat generalizes: masking changes the sampling distribution. This is the architectural reason Verso keeps SAP/repair as the default and treats constrained decoding as an opt-in fast-path, not the primary path.

## XGrammar

### What It Is

XGrammar is the **default** constrained-decoding backend for vLLM, SGLang, TensorRT-LLM, and MLC-LLM (see `infra-serving.md`). It compiles JSON-schema/regex/EBNF/structural-tag → a token bitmask each decode step, with "near-zero overhead" and "up to 100x speedup over existing solutions" (KNOWN, arXiv:2411.15100 abstract). Architecturally it is *not* an eager full-vocab `Index` like Outlines — it is a **pushdown automaton (NPDA)** matcher plus an *adaptive* mask cache that splits the vocabulary into context-independent tokens (precheckable, cached) and context-dependent tokens (checked at runtime against the persistent stack). The four core techniques (KNOWN, paper): (1) split vocab into context-independent vs context-dependent tokens; (2) grammar transformations that *expand grammar context* to shrink the context-dependent set; (3) a persistent stack to accelerate context-dependent checks; (4) co-design with the inference engine to **overlap grammar mask computation with GPU execution** (the grammar engine runs on CPU while the GPU does the matmul, hiding the mask cost). For Verso, XGrammar is the production reality of "what the engine does when I send a `json_schema`," and **TagDispatch** changes how Verso should frame a tool-call turn.

### The Per-Decode-Step Engine Contract (KNOWN — `include/xgrammar/matcher.h` + `python/xgrammar/matcher.py`)

`GrammarMatcher` (`matcher.h:67-185`) is the stateful NPDA matcher — "it keeps track of the current state of the matching process by maintaining several stacks internally as possible paths in the NPDA. It also supports backtracking." The per-step loop an engine runs (verbatim from the header example, `:51-65`):
1. `matcher = GrammarMatcher(compiled_grammar, ...)`.
2. Each step: **`matcher.FillNextTokenBitmask(&bitmask, index)`** (`:111`) — fills the bitmask with the acceptable next tokens; returns `false` if the mask is all-true (no masking needed — a fast-path the engine can skip).
3. Engine applies the mask: **`apply_token_bitmask_inplace(logits, bitmask)`** (`matcher.py:58`) — sets disallowed logits to `-inf`. The bitmask is an **int32** tensor of shape `(batch_size, ceil(vocab_size/32))` (`matcher.py:15-21`) — one bit per token (int32 not uint32 only because old PyTorch lacks uint32, `:33-34`).
4. Sample, then **`matcher.AcceptToken(token_id)`** (`:92`) — advance the NPDA; returns whether accepted.
5. `IsTerminated()`/`IsCompleted()` check stop conditions; `Rollback(n)` (`:150`) undoes n tokens (needed for **speculative decoding** — XGrammar can verify/reject a draft tree via `TraverseDraftTree`, `:130-136`, which DFS-fills a bitmask per draft node). `FindJumpForwardString()` (`:143`) returns the longest forced continuation for **jump-forward decoding** (skip tokens that the grammar fully determines — this is the compressed-FSM jump-forward that SGLang's `outlines_jump_forward.py` also exposes, cross-ref `infra-serving.md`/SGLANG). `BatchGrammarMatcher` (`:196-252`) multi-threads `FillNextTokenBitmask`/`AcceptToken` across the batch.

This contract — `Fill bitmask → apply (-inf) → sample → AcceptToken → maybe Rollback` — is byte-for-byte the same shape as Outlines' `Guide`/`fill_next_token_bitmask`/`apply_token_bitmask`. **The bitmask is the universal grammar↔sampler interface.** Verso never calls these; it must only know that this is what the engine does so it can reason about latency (the mask cost is hidden behind the GPU step by technique #4) and about which engine features (jump-forward, spec-decode rollback) its constraints can exploit.

### GrammarCompiler = the Cross-Grammar / Adaptive Mask Cache (KNOWN — `include/xgrammar/compiler.h:50-111`)

`CompiledGrammar` (`compiler.h:28-48`) is the preprocessing result (grammar + tokenizer adaptive-mask cache); it knows its `MemorySizeBytes()` and can `SerializeJSON()`/`DeserializeJSON()` — so a compiled grammar can be persisted and shipped, not recompiled. **`GrammarCompiler`** (`:57-111`) is the cache, constructed *once per vocabulary*: `GrammarCompiler(tokenizer_info, max_threads=8, cache_enabled=true, max_memory_bytes=-1)`. It exposes `CompileJSONSchema`, `CompileBuiltinJSONGrammar`, `CompileGrammar(ebnf)`, `CompileRegex`, `CompileStructuralTag`, and cache controls `ClearCache`/`GetCacheSizeBytes`/`CacheLimitBytes`. The cache is what the spec calls the **Cross-Grammar Cache**: substructure compilation is reused across requests, and `max_memory_bytes` bounds it (LRU-style eviction implied by the byte cap). `max_threads=8` is the multi-threaded JIT compile. `CompileJSONSchema` flags worth noting: `any_whitespace=true` (contrast Outlines' pinned `[ ]?`), `strict_mode=true` (reject `additionalProperties`), `max_whitespace_cnt` (cap whitespace runs — same small-model pathology Outlines pins).

**Verso implication:** the compiler is keyed by `(tokenizer/vocabulary)`. Verso must instantiate one compiler per model and reuse compiled grammars across agent turns — never recompile a schema per call. A schema object should be a long-lived, cacheable artifact.

### The Adaptive Token Mask Cache — accepted / rejected / uncertain (KNOWN — `cpp/compiled_grammar.cc:16-67`)

This is XGrammar's core algorithmic contribution and the reason it's faster than Outlines. For each grammar rule-position, `AdaptiveTokenMask` precomputes a partition of the vocabulary into three sets: **`accepted_indices`** (tokens always legal here regardless of stack — context-independent accept), **`rejected_indices`** (always illegal here — context-independent reject), and **`uncertain_indices`** (context-dependent — whether they're legal depends on the full NPDA stack, so they must be checked at runtime). The accepted+rejected sets are cached once at compile time; only the (small) uncertain set is interpreted per decode step against the persistent stack. A storage optimization (`:28-42`): store whichever of accepted/rejected is *smaller* as a sparse index list, or switch to a `DynamicBitset` (`kAcceptedBitset`) once both exceed `USE_BITSET_THRESHOLD` — minimizing the cache's memory footprint. The grammar-context-expansion transformation (paper technique #2) inlines rule context specifically to *shrink the uncertain set*, pushing more tokens into the context-independent (cacheable) buckets. At decode time the engine fills the bitmask from the cached accepted/rejected sets in O(1) and only runs the NPDA matcher on the uncertain tokens — that's the "near-zero overhead." **Verso takeaway:** a schema that produces few context-dependent token positions (flat structure, literal-heavy, narrow value types) compiles to a smaller uncertain set and decodes faster; deeply-nested unions with open string fields blow up the uncertain set. Schema shape directly controls constrained-decode latency.

### TagDispatch — Mid-Request Grammar Switching (KNOWN — `python/xgrammar/structural_tag.py` + `grammar.h:137 FromStructuralTag`)

This is the finding that reshapes how Verso frames a tool-calling turn. A **structural tag** (`Grammar::FromStructuralTag`, compiled by `CompileStructuralTag`) lets one grammar switch between free generation and constrained generation *at tag boundaries within a single request*. The relevant format is **`TriggeredTagsFormat`** (`structural_tag.py:156-209`): given `triggers: List[str]` and `tags: List[TagFormat]` (each `TagFormat(begin, content, end)` where `content` is e.g. a `JSONSchemaFormat`), the grammar "allow[s] any output until a trigger is encountered, then dispatch[es] to the corresponding tag; when the end tag is encountered, the grammar will allow any following output, until the next trigger." Each trigger must be a prefix of exactly one tag's `begin`. The documented accepted output (`:190-194`):
```
any_text<function=func1>{"name":"John","age":30}</function>any_text1<function=func2>{...}</function>any_text2
```
So a single constrained request models exactly `<free reasoning> + <trigger> + <begin tag> + <JSON tool args, schema-constrained> + <end tag> + <free continuation> + …`. `at_least_one`, `stop_after_first`, and `excludes` tune it. `TokenTriggeredTagsFormat` (`:212-231`) does the same at the token-ID level (dispatch on a trigger *token* rather than a string — relevant when the chat template emits a special tool-call token). `TagsWithSeparatorFormat` (`:234+`) constrains a separated list of tags with no free text.

The low-level form is `StructuralTagItem{begin, schema, end}` (`grammar.h:23-30`) — a begin marker, a JSON-schema for the content, and an end marker. The high-level convenience is **`openai_tool_call_schema.py`**: XGrammar ships a builtin structural-tag builder that takes an OpenAI Chat-Completions `tools[]` array + `tool_choice` and compiles the *whole tool set* into one TagDispatch grammar — each tool becomes a tag whose `content` is that tool's `function.parameters` schema, triggered by the tool-call open marker, with `tool_choice="required"` forcing at least one and `"auto"` allowing free text. So an engine can accept the standard OpenAI tools payload and get correct multi-tool constrained decoding for free. `Grammar` also exposes `FromEBNF`, `FromJSONSchema(strict_mode)`, `FromRegex`, and the combinators **`Grammar::Union(grammars)`** / **`Grammar::Concat(grammars)`** (`grammar.h:93-162`) — so grammars compose, which is how a TagDispatch is assembled from per-tool sub-grammars.

This is the answer to the spec's open question: **a tool-call turn is ONE request with a TagDispatch grammar, not two sequential requests.** The model reasons in free text, the trigger `<function=` flips the grammar into the per-tool JSON schema, the `</function>` flips it back to free text — all in one decode loop, so the reasoning and the structured args share a single KV cache and a single sampling pass.

### Why XGrammar (vs Outlines) for the eager/lazy axis (INFERRED from the two codebases)

Outlines pays a full O(states×vocab) `Index` build upfront, then per-step is a hashmap lookup. XGrammar instead precomputes only the **context-independent** token mask (the bulk of the vocab that a grammar position accepts/rejects regardless of stack contents) and resolves the small **context-dependent** set at runtime against its persistent stack — so compilation is far cheaper (the paper claims ~6x faster compile in the spec's framing) at the cost of a tiny per-token interpretation, which technique #4 hides behind the GPU. For an *agent* that switches schemas frequently (every tool turn), cheaper compilation + a cross-grammar cache + TagDispatch is strictly better than Outlines' rebuild-the-whole-Index model. This is why the major engines default to XGrammar.

**For Verso:**
- **Model a tool-call turn as ONE structured request with a TagDispatch/structural-tag grammar where the engine supports it.** Verso's context builder should emit a `TriggeredTagsFormat`-equivalent (triggers = tool-call open markers; per-tool `content` = that tool's arg schema) rather than splitting reasoning and tool-args into two calls. One request = one KV cache = lower latency and coherent reasoning→args. Fall back to two calls (or to SAP repair) only when the provider/engine lacks structural tags.
- **Reuse compiled grammars across turns; one compiler per model vocabulary.** Mirror `GrammarCompiler(cache_enabled=true, max_memory_bytes=...)`: Verso should hold a per-model grammar-compile cache bounded by bytes, keyed by schema, and never recompile a schema it has seen. Persist hot grammars via the `SerializeJSON` path if cold-start matters.
- **The grammar↔sampler contract Verso targets is `bitmask → apply(-inf) → sample → AcceptToken → Rollback`.** When Verso configures structured output on a local engine, it is implicitly relying on this loop; Verso should expose the engine features it unlocks — **jump-forward** (free, schema-determined spans cost no model calls) and **spec-decode rollback** — as knobs, not hide them.
- **`any_whitespace`/`max_whitespace_cnt` matters.** When emitting schemas for XGrammar, cap whitespace (the same small-model pathology Outlines pins with `[ ]?`); leaving `any_whitespace=true` unbounded invites whitespace drift on weak models.

## Guidance + llguidance

### What It Is

Guidance (Microsoft) is the most explicit published model of **interleaving Python control flow with constrained generation** — exactly Verso's agent loop. The Python `guidance` package is the authoring DSL (`gen()`, `select()`, the `@guidance` decorator, `system()/user()/assistant()` context managers); the Rust `llguidance` crate is the backend that turns those grammars into per-token masks. The architectural contrast with Outlines/XGrammar: llguidance computes masks **lazily** (an Earley parser over a regex-derivative lexer, traversing the token trie at request time) with negligible startup cost, vs Outlines' eager full-`Index` build. OpenAI credited llguidance as foundational for its Structured Outputs.

### The `guidance` Programming Model (KNOWN — `guidance/_guidance.py`, `library/_gen.py`, `library/_role.py`)

`@guidance` (`_guidance.py:17-41`) decorates a Python function into a `GuidanceFunction`. The key parameter is **`stateless`** (`:20,54`): a `stateless=True` function builds a pure grammar fragment (no model interaction) that can be *composed* into a larger grammar; a stateful one interleaves real generation. `_in_stateless_context` (a `ContextVar`, `:14`) tracks whether we're currently assembling a grammar so nested functions know not to call the model. This is the composability primitive: grammars are values you build with Python (loops, conditionals, function calls) and then execute.

`gen()` (`library/_gen.py:13-29`) is the core generation primitive: `gen(name=None, *, max_tokens, regex=None, stop=..., stop_regex=..., tools=None, temperature=..., n=1, ...)`. It generates until a stop criterion, optionally constrained by `regex`, optionally interleaving `tools` (tool calls mid-generation, `hide_tool_call`/`tool_choice`). `name` captures the result into `lm[name]`. The `system()/user()/assistant()` context managers (`library/_role.py:8-48`) wrap a block in `RoleStart`/`RoleEnd` AST nodes — so the chat structure is part of the same grammar tree as the constrained spans. The whole program compiles to one grammar that llguidance executes, with the model only consulted where `gen` appears.

**The grammar AST (reimplementation model — `guidance/_grammar.py`).** Every primitive returns a `GrammarNode`, and they compose: `regex(pattern) -> RegexNode` (`:23`); `gen(...)` (`:27`) builds a gen node bounded by stop/regex; **`select(options, recurse=...)`** (`:61-115`) builds an *alternation* node — each option is coerced to a `GrammarNode` (a bare `str`/`int`/`float` becomes a literal) and combined into an N-way OR; `repeat(value, min, max)` (`:117`) is bounded repetition; `capture(value, name, list_append)` (`:175`) wraps a node so its matched span is saved to `lm[name]`; `subgrammar(body, ...)` (`:182`) nests; `token_limit(value, max_tokens)` (`:141`) and `with_temperature(value, temp)` (`:156`) attach per-span generation settings to a `RuleNode`. So a "structured turn" is literally an expression tree of these nodes, built with ordinary Python, compiled once, executed by llguidance. **For Verso this is the cleanest published model of "grammar-as-value":** Verso's context layer can represent a constrained turn as a composable tree (role blocks + literal spans + `gen(regex=)` spans + `select` alternations + `capture`s) rather than a string template, and compile it to whatever the target engine accepts.

### llguidance: Lazy Mask Computation (KNOWN — `llguidance/parser/src/tokenparser.rs` + `parser/src/matcher.rs` + `parser/src/earley/`)

The public per-step contract (`matcher.rs`) mirrors XGrammar's but is lazy: `consume_token(tok)` / `consume_tokens(&[tok])` (`:74-86`) advance the parser; **`compute_mask() -> SimpleVob`** (`:102`, a bitset over the vocab) is the allowed-token mask for the *next* step; `compute_mask_or_eos`, `rollback(n)` (`:93`), `reset`, `is_stopped`/`stop_reason`, `validate_tokens` (`:178`, batch-check a token sequence), and the fast-forward family `compute_ff_tokens`/`consume_ff_tokens`/`compute_ff_bytes` (`:140-155`).

**`compute_mask` is computed on demand each step** (`tokenparser.rs:461-519`), not precomputed into a table. Steps: (1) `compute_mask_start_time = Instant::now()` and record into `perf_counters().compute_mask` — llguidance times every mask (this is where the ~50µs/token figure is measured). (2) **Fast-forward shortcut** (`:476-495`): if `can_force_bytes()`, take cached `ff_tokens()`; if the grammar forces a specific next token, return a **singleton mask** for it immediately (`singleton_token_set(t)`) — no trie traversal needed (jump-forward decoding: the model isn't even consulted for grammar-determined tokens). (3) Otherwise `compute_bias(&prefix)` (`:497`) does the real work: the **Earley parser** (`earley/parser.rs:2732 compute_bias`) traverses the **token trie** (`toktrie::TokTrie`), and at each trie node consults the **regex-derivative lexer** (`earley/lexer.rs`, a `RegexVec` DFA with `transition`/`next_byte`) to prune whole subtrees of tokens that can't extend the current parse — this is why it's lazy: it only explores trie branches the grammar allows, computing the mask by *derivative* rather than enumerating the full vocab. (4) If `is_accepting()`, OR-in the EOS tokens (`:503-509`). (5) If the mask is all-zero → stop with `NoExtensionBias`. A `slicer` (`earley/slicer.rs`) caches per-slice tries to amortize repeated traversals.

The "hidden" mechanism (`parser.rs:2757-2764`): for `gen(stop="foo")`, the bytes of `foo` are generated but marked hidden so the captured result excludes them — Verso needs an equivalent if it adopts stop-strings that shouldn't appear in the output.

**The slicer — how the lazy mask is made cheap (KNOWN — `earley/slicer.rs:14-55`).** The naive lazy approach (test every vocab token against the lexer each step) would be slow. llguidance instead precomputes, per *regex slice* of the grammar, a `TokenizerSlice` holding: the slice regex, a `mask_with_children` (`SimpleVob` token bitset of all tokens matching that regex, built once by `rx.is_match_bytes(token_bytes)` over the vocab, `:39-45`), filtered tries `trie_with_children`/`trie_without_child[i]`, and nested `children` slices (each a subset). The regex engine is **`derivre`** — a *regex-derivative* matcher: instead of a precompiled DFA over the whole alphabet, it computes the derivative of the regex w.r.t. each input byte on demand, so it never materializes the full transition table (the lazy analogue of Outlines' eager DFA). At mask time, `compute_bias` walks the token trie but prunes whole subtrees using these precomputed slice masks intersected with the current Earley/lexer state — so it only pays for the tokens the grammar position could plausibly accept. This slice cache is what gets the per-token cost down to the ~50µs range without an upfront full-vocab `Index` build.

### Eager (Outlines) vs Lazy (llguidance) — the tradeoff Verso must pick per use case (INFERRED)

- **Outlines/outlines-core (eager):** build the entire `state→{token→state}` `Index` upfront (O(states×vocab)). Per-token decoding = one hashmap lookup (nanoseconds). **Wins when:** the same schema is reused for many long generations (amortize the build), and you can afford the compile latency + memory.
- **llguidance (lazy):** ~zero startup, compute each mask by Earley-derivative trie traversal (~50µs/token measured). **Wins when:** schemas change frequently (every agent turn has a different tool schema), short generations, or you can't pay an upfront compile. The per-token cost is higher but there's no build phase to amortize.
- **XGrammar (hybrid):** precompute only context-independent tokens, resolve context-dependent ones at runtime, overlap with GPU — splitting the difference, which is why engines default to it.

For Verso's agent workload (frequently-changing tool schemas, often short structured spans), the lazy/hybrid end is usually correct; the eager `Index` is only worth it for a hot, stable schema generated at length.

**For Verso:**
- **The `@guidance` `stateless` grammar-as-value pattern is the strongest prior art for Verso's context-engineering DSL.** A Verso "structured turn" should be expressible as composable grammar fragments (role blocks + free `gen` spans + constrained `gen(regex=...)`/`select` spans) assembled with ordinary Python control flow, compiled once, executed by whatever backend the target engine provides. The `_in_stateless_context` flag is the mechanism that lets nested helpers build grammar without firing the model — adopt it if Verso builds grammars compositionally.
- **Pick backend by schema churn, not dogma.** Verso's schema compiler should know both costs: for a stable schema generated at length → eager `Index` (Outlines); for per-turn-varying tool schemas / short spans → lazy `compute_mask` (llguidance) or hybrid (XGrammar). Expose this as a backend-selection policy, defaulting to the engine's native backend (XGrammar on vLLM/SGLang).
- **Adopt the lazy mask contract shape for any Verso-side grammar matcher:** `consume_token → compute_mask → (apply) → sample → consume`, with `rollback` for spec-decode and `compute_ff_tokens` for jump-forward. Time every `compute_mask` (llguidance records it per step) so Verso can surface per-token constraint overhead in its observability layer.
- **Implement the "hidden bytes" rule for stop strings.** If Verso supports `gen(stop=...)`-style termination, the stop text must be generatable but excluded from the captured value — copy llguidance's hidden-start mechanism.

## Mirascope

### What It Is

Mirascope is the explicit "no-magic" thin-provider-abstraction reference — the closest public analogue to Verso's pluggable-edges design. The v2 codebase (`python/mirascope/llm/`) makes structured output a first-class, *explicitly-chosen* mode rather than an inferred one. The relevant piece: `llm.format(Model, mode=...)` produces a `Format` object that the provider adapter consumes; the three modes are the same decision Verso's output module makes on every turn.

### The Three Formatting Modes (KNOWN — `formatting/types.py:44-74`, `formatting/format.py`)

`FormattingMode = Literal["strict", "json", "tool"]` (`types.py:44-47`) — plus an internal `"parser"` for custom output parsers. The semantics are documented verbatim:
- **`"strict"`** (`types.py:52-55`): use the provider's native strict structured-outputs (OpenAI `response_format: json_schema` with `strict:true`). "Not all providers or models support it, and may not be compatible with tool calling" — raises `llm.FeatureNotSupportedError` if unsupported. This is the only mode with a *guarantee*.
- **`"json"`** (`types.py:57-62`): ask for JSON as text. "If the provider has explicit JSON mode, it will be used" — otherwise the schema is injected into the system prompt and the output is parsed best-effort (no guarantee the model obeys). May be incompatible with tool calling.
- **`"tool"`** (`types.py:64+`): forced tool calling — Mirascope constructs a synthetic tool whose parameters are the target schema and forces the model to call it.

**The key Verso lesson is in the "auto" note (`types.py:74`):** "When `llm.format` is not used, the provider will automatically choose a mode at call time." So the *provider adapter owns the fallback ladder* — each provider knows its own capabilities and picks strict → tool → json. This is exactly the inverse of leaking a 40-mode enum to the caller (Instructor's older design); Mirascope pushes the mode decision into the adapter and exposes only the 3 semantic intents. `to_format(formattable, default_mode)` (`format.py:271-291`) is where a bare model is wrapped with the provider's default mode.

### The Universal Format Tool (KNOWN — `formatting/format.py:96-139`)

For `"tool"` mode, `create_tool_schema()` builds one synthetic tool named `FORMAT_TOOL_NAME`: `parameters = ToolParameterSchema(properties=<model schema properties>, required=<all keys>, additionalProperties=False)`, `$defs` carried through, `strict=None` (let the provider decide whether to set strict). Description: `"Use this tool to extract data in {name} format for a final response."` The model is forced to call this one tool, and its arguments ARE the structured output. Note `required = list(properties.keys())` — **every field is marked required** in the tool schema (OpenAI strict mode requires all-required + `additionalProperties:false`; optionality is handled by the model annotation — the same all-required + `additionalProperties:false` rewrite DSPy applies for OpenAI strict mode, per the structured-output spec's "Already Covered" DSPy notes).

`formatting_instructions()` (`format.py:74-94`): in `"tool"` mode it appends `TOOL_MODE_INSTRUCTIONS`; in `"json"` mode it appends `JSON_MODE_INSTRUCTIONS.format(json_schema=<indented schema>)` — the schema is literally dumped into the system prompt. A model can override by defining a `formatting_instructions` classmethod (return `None` to disable all prompt modification). This is the "prompt-as-schema" compilation (schema dumped into the prompt + parser on the output) — the same pattern DSPy's `JSONAdapter`/`ChatAdapter` use.

### Streaming Partials (KNOWN — `formatting/partial.py`)

Same silviumarcu `Partial[T]` lineage as Instructor (`partial.py:1-7` cites the same pydantic issue). It recursively makes all fields optional via `create_model`, **caches the partial model per wrapped class** (`_partial_model_cache`, `:19,92-93,129`) so the optional-field rewrite is done once, and feeds growing chunks through the same parse-then-construct path. Verso can reuse the identical pattern.

**For Verso:**
- **Expose 3 semantic format intents, not a provider-mode enum; let the adapter pick.** Verso's output module should offer `strict` / `tool` / `json` as the caller's *intent*, and have each provider edge own the fallback ladder (try strict → tool → json, raise a typed `FeatureNotSupported` only when the caller pinned an unsupported mode). This combines Instructor's capability map (the adapter knows what's possible) with Mirascope's clean caller surface (3 intents, not 40 modes). Default (no explicit format) = adapter auto-selects the most reliable supported mode.
- **Use one universal "format tool" for tool-mode extraction.** A single synthetic forced tool whose params = the target schema, with `additionalProperties:false` and all-required (optionality via annotation), is the cleanest tool-mode extraction. Reuse it across providers; only the wire serialization differs per edge.
- **Cache the partial-model rewrite per class** (Mirascope's `_partial_model_cache`) — the optional-field transform is pure and should be memoized, not recomputed per stream.
- **Prompt-as-schema for json mode.** When falling back to `json` mode, inject the indented JSON schema into the system prompt (Mirascope's `JSON_MODE_INSTRUCTIONS`) and parse with the jsonish waterfall — this is the universal lowest-common-denominator path for providers with no native structured output.

## Guardrails AI

### What It Is

Guardrails is the reference for "output validation as a composable pipeline." It is **post-generation only** — no constrained decoding. Its value to Verso is two clean contracts: the `Validator` ABC (`validate → Pass/Fail`) and the `OnFailAction` decision tree (what to do when a validator fails — fix locally, reask the LLM, filter, refrain, or raise). The RAIL XML spec is heavyweight and *not* worth adopting; the two contracts are.

### The Validator Contract (KNOWN — `guardrails/validator_base.py:92`, `classes/validation/validation_result.py`)

A `Validator` (`validator_base.py:92`) is constructed with an `on_fail` policy and implements `validate(self, value, metadata: dict) -> ValidationResult` (`:206`). The result is one of two subclasses (`validation_result.py:35-58`): **`PassResult`** (value is acceptable) or **`FailResult`** carrying `error_message`, an optional **`fix_value`** (the corrected value the validator proposes), and optional `error_spans` (which parts of the value failed — for surgical fixes). `validate_stream` (`:266`) exists for incremental validation, splitting the stream into sentences (`split_sentence_*`, `:40-87`) so a validator can run on complete sentences as they arrive rather than waiting for the full output. This is a clean separation: the validator only *judges and proposes*, it does not decide *what happens* on failure.

### The Reask-on-Fail Decision Tree (KNOWN — `types/on_fail.py:6-31` + `validator_service/validator_service_base.py:73-117`)

`OnFailAction` (`on_fail.py:24-31`) is the full policy enum: `FIX`, `REASK`, `FIX_REASK`, `FILTER`, `REFRAIN`, `NOOP`, `EXCEPTION`, `CUSTOM`. Default when unspecified is **`EXCEPTION`** (`validator_base.py:139-140`). `perform_correction(result, value, validator, rechecked_value)` (`validator_service_base.py:73-117`) is the dispatch that turns a `FailResult` into an outcome:
- **`FIX`** (`:81-84`) → return `result.fix_value` (apply the validator's static correction; *no LLM call*).
- **`FIX_REASK`** (`:85-95`) → apply `fix_value`, **re-run the validator on the fixed value**; if it *still* fails, escalate to a `FieldReAsk(incorrectValue=fixed_value, failResults=[result])`. This is the "try a cheap local fix first, only burn an LLM round-trip if the fix didn't satisfy" optimization.
- **`REASK`** (`:100-104`) → emit `FieldReAsk(incorrectValue=value, failResults=[result])` — the Guard collects these and issues a *new LLM call* with the failure context embedded.
- **`EXCEPTION`** (`:105-109`) → raise `ValidationError` with the joined error messages.
- **`FILTER`** (`:110-111`) → return a `Filter()` sentinel (drop the failing field from the output).
- **`REFRAIN`** (`:112-113`) → return `Refrain()` (suppress the entire response).
- **`NOOP`** (`:114-115`) → return the value unchanged (log only).
- **`CUSTOM`** → call the user-supplied `on_fail_method(value, result)`.

The Guard runs validators (sequentially or async-parallel via the two `validator_service` implementations), collects `FieldReAsk`s, and **only issues a reask LLM call when at least one validator returned REASK/FIX_REASK-that-still-failed.** That is the precise reask-budget decision: a failure is *not* automatically an LLM round-trip — `FIX`, `FILTER`, `REFRAIN`, `NOOP` resolve without one.

**For Verso:**
- **Adopt the `validate → Pass/Fail(fix_value, error_message, error_spans)` Validator contract.** Verso's reliability layer should let validators *only judge and propose* a fix; the policy of what to do on failure is separate (the caller's, not the validator's). The `error_spans` field is the enabler for surgical fixes (patch just the bad span) vs whole-value regeneration.
- **Adopt the `OnFailAction` policy enum as Verso's per-validator failure policy** — especially `FIX` (cheap local correction, no LLM call), `FIX_REASK` (local fix → recheck → only reask if still bad), and `REASK` (escalate to LLM). The key budget rule: **a validation failure is not automatically a reask.** Most failures should resolve via `FIX`/`FILTER`/`NOOP` without spending a model round-trip; reask is the expensive last resort, which is exactly how Verso's retry budget should be spent.
- **Reask carries structured failure context, not just an error string.** `FieldReAsk(incorrectValue, failResults)` is richer than Instructor's `str(exception)` — it keeps the bad value *and* the structured fail results, so the regeneration prompt can show the model exactly what it produced and why each part failed. Verso's reask should carry both (this also unifies with Instructor's reask: feed the validation errors + the prior output back).
- **Run validators on sentence boundaries during streaming** (`validate_stream`) so output-quality validators don't block until the full response arrives. **Do NOT adopt the RAIL XML spec** — it is heavyweight and offers nothing the Validator+OnFailAction contracts don't.

## Cross-System Synthesis → Verso

### The two halves of Verso's structured-output layer

1. **Universal post-hoc path (always available, the default):** model emits text → **jsonish waterfall** (strict JSON → markdown-fence extract → grep-embedded-JSON → char-level repair → as-string) → **schema-guided coercion ranked by a typed edit-cost** (`Flag` table, not Levenshtein) → **validate** (Pydantic + Guardrails-style Validators) → on failure, **reask** with structured error context, governed by an `OnFailAction`-style policy where reask is the last resort. This works on every provider because Verso owns no inference. BAML supplies the parser+cost-function; Instructor supplies the reask loop + mode map; Guardrails supplies the validate/fix/reask policy; Mirascope supplies the clean 3-intent caller surface.
2. **Constrained-decoding fast-path (local engines only, opt-in):** Verso emits a clean `json_schema`/`regex`/structural-tag down the wire; the engine (XGrammar default, Outlines or llguidance alternatives — see `infra-serving.md`) compiles it and masks per token. Verso's job is to *produce a good grammar* (pinned whitespace, minimal redundant tokenization, TagDispatch for tool turns) and *cache it per (schema, model)*, never to decode.

### Decisions this note settles for Verso

- **Mode surface = 3 intents (`strict`/`tool`/`json`), adapter-owned fallback.** Mirascope's clean surface + Instructor's per-provider capability map. Default = adapter auto-selects most reliable supported mode.
- **Tool-call turn = ONE request with a TagDispatch grammar** where supported (XGrammar structural tags), not two sequential calls. Falls back to SAP repair otherwise.
- **Streaming = construct-not-validate.** All-fields-optional partial model, parse the growing buffer (jiter `trailing-strings`), `model_construct` until the root closes, then `model_validate`. Type-driven done/needed annotations (BAML) decide what partial nodes to emit.
- **Repair cost function = typed `Flag` edit-distance** with the BAML penalty cliffs (`SingleToArray`=1 … `DefaultButHadValue`=110, ×10 per child level), selected via a `pick_best` comparator with semantic tie-breaks — not raw string distance.
- **Reask is the expensive last resort.** Local fixes (`FIX`), filters, and partial acceptance resolve most failures; only escalate to a model round-trip on genuine validation failure, with structured error context (incorrect value + fail results), and bound the loop with per-attempt usage accounting.
- **Cache compiled grammars and partial-model rewrites per key.** Grammar compilation (eager Index or XGrammar cache) and the optional-field partial transform are pure and must be memoized across agent turns.
