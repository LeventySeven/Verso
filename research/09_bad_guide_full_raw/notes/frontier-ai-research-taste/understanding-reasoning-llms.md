## Full Digest

Raschka's article is the clearest public synthesis of the four distinct engineering paths for building reasoning models, anchored in the DeepSeek-R1 family as the most technically transparent example. The article's organizing question: what is "reasoning" in the context of LLMs, and how do you build it?

### Definition: What Is a Reasoning Model?

Raschka's definition is functional: reasoning models are LLMs specialized for "complex, multi-step generation with intermediate steps." The canonical examples are math problems (AMC, AIME, MATH benchmark) and competitive coding. The counter-examples — tasks that do NOT require reasoning models — are equally specific: "summarization or translation tasks," straightforward factual questions like capital cities. The practical prescription: "use the right tool (or type of LLM) for the task." Reasoning models are "more expensive to use, more verbose, and sometimes more prone to errors due to 'overthinking.'"

### The Four Engineering Paths

#### Path 1: Inference-Time Scaling

No modification to the base model. The mechanism is increased compute at generation time:
- **Chain-of-thought (CoT) prompting**: "think step by step" elicits intermediate reasoning steps
- **Majority voting**: generate multiple answers, select via vote
- **Beam search and other search algorithms**
- **Process Reward Models (PRM)** and **Monte Carlo Tree Search (MCTS)**

The DeepSeek-R1 technical report categorizes explicit inference-time scaling methods as "unsuccessful attempts" — meaning they tried and found them insufficient on their own. However, Raschka notes that implicit inference-time scaling occurs naturally in trained reasoning models: they generate longer responses, which is itself a form of spending more compute at inference.

#### Path 2: Pure Reinforcement Learning (R1-Zero approach)

DeepSeek-R1-Zero: built on the 671B DeepSeek-V3 base model, trained with RL only — no supervised fine-tuning (SFT) stage. This is termed "cold start" training.

**Reward structure:**
- **Accuracy reward**: for coding, a LeetCode-style compiler verifies correctness (deterministic); for math, a deterministic symbolic verifier
- **Format reward**: an LLM judge ensures reasoning appears inside `<think>` tags before the final answer

The key finding: the model exhibited an emergent "Aha!" moment — it began generating reasoning traces spontaneously despite receiving no explicit training to do so. The model discovered that showing its work improved its own accuracy. This is the "verifiable reward goes vertical" principle: when feedback is binary and deterministic (right/wrong from a compiler or verifier), RL produces rapid improvement without needing human-labeled preference data.

RLVR (Reinforcement Learning with Verifiable Rewards): DeepSeek's specific contribution is eliminating both the reward model AND the critic model (versus standard RLHF which requires both). The algorithm is GRPO (Group Relative Policy Optimization), "a variant of PPO that enhances mathematical reasoning abilities while concurrently optimizing memory usage." GRPO samples multiple answers, computes relative advantages across the group, eliminates the separate critic — dramatically reducing training infrastructure.

**Limitation:** R1-Zero, despite showing emergent reasoning, performs worse than R1 (the SFT+RL version) overall. It also exhibits language mixing (reasoning in one language, answering in another) and less consistent formatting.

#### Path 3: SFT + RL (DeepSeek-R1 full pipeline)

The full DeepSeek-R1 pipeline is a five-stage process:
1. R1-Zero generates "cold-start" SFT data (reasoning traces from pure RL)
2. Instruction fine-tuning on this cold-start data
3. First RL stage with three reward types: accuracy (deterministic), format (structure), and consistency (prevents language mixing)
4. Generate 600K Chain-of-Thought examples + 200K knowledge-based examples from this checkpoint
5. Final instruction fine-tuning on all 800K samples, followed by a final RL stage using rule-based accuracy rewards for math/coding AND human preference labels for other task types

**Result:** "The final model, DeepSeek-R1 has a noticeable performance boost over DeepSeek-R1-Zero thanks to the additional SFT and RL stages." Competitive with OpenAI o1.

#### Path 4: Distillation (Pure SFT on Reasoning Teacher Data)

Smaller models trained on the SFT dataset generated by R1-Zero and R1. Not classical knowledge distillation — the smaller model never sees the teacher's logits, only the teacher's output text.

**Target models and results:**
- Llama 8B, Llama 70B
- Qwen 0.5B, 1.5B, 7B, 14B, 32B

**Key finding:** Distillation outperformed pure RL for smaller models. Qwen-32B trained with pure RL significantly underperformed both distilled variants. Llama 8B with pure SFT distillation outperformed R1-Zero despite being 84x smaller in parameter count.

**Why:** RL requires a base model with sufficient capacity to discover reasoning behaviors from reward signal alone. Small models don't have this capacity. Distillation transfers the already-discovered behaviors directly.

### Budget-Friendly Alternatives

- **Sky-T1** (32B, $450 total training cost): 17K SFT samples, distillation-based, achieves approximately o1-level performance on relevant benchmarks
- **TinyZero** (3B, <$30): demonstrates emergent self-verification via pure RL

These demonstrate that the key ingredient is not raw compute but the quality of the training signal (verifiable rewards or high-quality reasoning traces).

### GRPO Technical Detail (from follow-up article)

Standard RLHF pipeline: policy model + reward model + critic model (value function). GRPO eliminates the critic by sampling K answers per prompt, computing which answers are above/below the group mean quality, and using those relative comparisons as the advantage signal. This:
- Removes the memory cost of a separate value model (significant for 671B-parameter training)
- Makes RL tractable on very large models
- Requires no human preference labels when rewards are verifiable (RLVR)

Known problems with GRPO/PPO for reasoning:
- **Length bias**: rewards inadvertently favor longer responses; solutions include token-level rewards focusing on critical steps, explicit length penalties, or Dr. GRPO (modified normalization)
- **Benchmark instability**: claimed improvements on small benchmarks (AIME24) are "highly unstable — random seed changes shift scores by several percentage points"
- **Small model limitations**: pure RL doesn't reliably produce emergent reasoning in models below ~32B parameters

### When NOT to Use Reasoning Models

Raschka's list of tasks where standard LLMs outperform or match reasoning models at lower cost:
- Summarization
- Translation
- Simple factual Q&A
- Creative writing
- Straightforward classification

Reasoning models are specifically for: math, coding, formal logic, multi-step planning, scientific problem-solving.

## VERSO RELEVANCE

### Finding 1: RLVR's binary deterministic feedback = the verifiable-reward principle operationalized [CONFIRMS §5.5 / §6.4]

The already-known principle "verifiable reward goes vertical" is confirmed with specific mechanism: deterministic binary feedback (compiler pass/fail, math verifier right/wrong) enables RL to work without human labels and without a learned reward model. For Verso's eval design (§5.5), this sharpens the `define_outcome(bounded)` rationale: evaluations should be designed to produce verifiable or near-verifiable signals wherever possible — not because rubrics are intellectually satisfying, but because they are the training signal that makes the system improvable without human labeling at scale. **Verdict: confirm §5.5.** confirm

### Finding 2: Distillation > pure RL for small models — implications for the model provider layer [SHARPENS §6.4]

The finding that distillation (SFT on reasoning traces) outperforms pure RL for models below ~32B changes the model selection calculus. For Verso's default model configuration: a 32B distilled reasoning model (e.g., Qwen-32B-Distill) may deliver better reasoning quality per dollar than a larger model with pure RL training. The role-tiered model architecture (cheap loop / mid retry / reasoning synthesis) should account for this: the "reasoning synthesis" tier is best served by a distilled model, not necessarily the largest model. The cheap loop tier definitely should NOT use a reasoning model (too verbose, too expensive, "prone to overthinking" on simple tasks). **Verdict: sharpen §6.4 — distilled reasoning models (32B class) are the recommended reasoning-tier default; full 671B-class models are overkill for most synthesis tasks.** sharpen

### Finding 3: Thinking tags `<think>...</think>` as structured context — explicit format hook [SHARPENS §5.1 / §5.2]

R1-Zero's format reward — an LLM judge verifying that reasoning appears inside `<think>` tags before the final answer — is now standard for reasoning models. Verso's loop infrastructure must handle this gracefully: the `<think>` content is intermediate reasoning that should be (a) captured in the event log for traceability, (b) NOT fed back into the next turn's context window verbatim (it's the model's scratchpad, not the conversation history), and (c) available to the eval layer as a trace-level signal. This is a concrete context engineering decision that falls out directly from reasoning model behavior. The already-known observation-masking compaction (N=10) should interact correctly with `<think>` output — reasoning traces should be masked/compacted more aggressively than tool results or assistant final answers. **Verdict: sharpen §5.2 — add explicit handling of reasoning model `<think>` output as a distinct observation class in the context engineering spec.** sharpen

### Finding 4: Benchmark instability of RLVR — eval robustness requirement [NEW-IDEA §5.5]

"Claimed RL improvements on small benchmarks are highly unstable — random seed changes shift AIME24 scores by several percentage points." This is a direct warning for Verso's eval design: single-run eval scores on narrow benchmarks are noisy. The judge-panel approach (multiple judges, bounded rubrics) partially addresses this, but Verso should also specify: evals should be run with multiple seeds or across multiple representative examples to get stable estimates. A single-run eval result that looks like a regression may be noise; a consistent direction across multiple runs is signal. **Verdict: new idea for §5.5 — add eval stability requirements (multiple-run aggregation, confidence intervals) as a first-class spec item.** adopt-now

### Finding 5: Domain generalization from logic puzzles to math — implications for eval breadth [NEW-IDEA §5.5]

"Training on logic puzzles transfers to math benchmarks, suggesting RL develops general reasoning independent of specific domains." For Verso's eval strategy: if Verso's evals are designed only around the user's specific task domain, they may miss reasoning capability that generalizes. The eval suite should include some domain-agnostic reasoning checks (can the agent decompose a novel multi-step problem, backtrack correctly, self-verify?) in addition to task-specific evals. This is related to but distinct from the "define_outcome(bounded)" principle — it's about eval suite composition, not individual eval design. **Verdict: new idea for §5.5 — add domain-agnostic reasoning probes to eval suite template.** lock-interface-defer

### Finding 6: "Overthinking" as an explicit cost to manage [SHARPENS §6.4 / §5.1]

Reasoning models are "more prone to errors due to 'overthinking.'" This is a known failure mode for production use. Verso's loop should provide a mechanism to cap reasoning verbosity — either via max_tokens on the thinking budget, or by explicitly passing a "brief reasoning" instruction when the task is simple. The role-tiered model architecture already handles this structurally (don't use a reasoning model for the cheap loop tier), but within the reasoning tier, overthinking needs active management. **Verdict: sharpen §5.1 — add reasoning verbosity control (thinking budget) as a loop parameter.** sharpen

### Finding 7: The cost of verifiable rewards — only math and code are naturally verifiable [SHARPENS §5.5]

RLVR's power comes entirely from tasks with deterministic correctness signals. "For other task types, human preference labels" are used in DeepSeek-R1's final RL stage. This means the verifiable-reward principle does NOT automatically generalize to agentic tasks involving open-ended decisions (e.g., "write a good email," "plan this project"). For Verso's eval design, the `define_outcome(bounded)` approach is the necessary substitute when true verifiability is unavailable — it trades exact determinism for reliable-enough LLM judgment at inference time. The specification should be explicit about this tradeoff: verifiable outcomes (task completion, tool call success, database consistency) > LLM-judged bounded rubrics > open-ended LLM critique. **Verdict: sharpen §5.5 — add explicit verifiability hierarchy to eval spec.** sharpen

## Summary Verdict

Raschka's article contributes three high-value findings for Verso: (1) the distillation > pure-RL finding for small models reshapes the model-tier recommendation in §6.4; (2) `<think>` tag handling is a concrete context engineering decision that needs explicit spec; (3) benchmark instability of RLVR evals is a direct argument for multi-run aggregation in Verso's eval infrastructure. The verifiability hierarchy (verifiable > bounded rubric > open critique) is the sharpest new addition to §5.5.
